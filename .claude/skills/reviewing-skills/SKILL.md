# Reviewing Skills（スキルのレビュー）

1つのスキルディレクトリを Anthropic 公式の作成ガイダンスに照らして監査し、作者がすぐ直せる
チェックリストを返す。目的は「点数を付けること」ではなく、実運用でスキルを静かに失敗させる要因
——発火しない description、コンテキストを圧迫する長すぎる本文、Claude が追えない参照、作業を
モデルに丸投げするスクリプト——を捕まえることにある。

判定基準の正本は [references/checklist.md](references/checklist.md) にある。このファイルを必ず読む
こと。各チェックが公式ドキュメントのどこに対応し、**なぜ重要か** が書かれている。ルールを鸚鵡返し
にするのではなく有用な修正を出すために、この「なぜ」が要る。

## ワークフロー

次のチェックリストを回答にコピーして、順に消し込みながら進める:

```
レビュー進捗:
- [ ] 1. 対象スキルを特定し、含まれる全ファイルを読む
- [ ] 2. 機械チェック用スクリプトを実行する
- [ ] 3. 判断が要る定性項目を SKILL.md を読んで評価する
- [ ] 4. レポートを書く: チェックリスト + 優先度付き修正 + 総合判定
```

### ステップ1: 特定して読む

対象の `SKILL.md` を見つける。ユーザーはディレクトリ・`SKILL.md` へのパス・名前だけ（「私の pdf
スキル見て」）のいずれかで渡してくる。最後のケースでは `~/.claude/skills/` と `.claude/skills/`
を探す。

`SKILL.md` 全体と、同梱される全ファイル（references・scripts・assets）を読む。実際に中身を見ずに
「参照が1階層か」「スクリプトが丸投げしているか」は判断できない。同梱ファイルが多い場合は、
SKILL.md から参照されているものを先に読む。

### ステップ2: 機械チェックを実行する

一部のチェックは機械的で、目視だと間違えやすい（文字数上限、name の正規表現、予約語、本文行数、
参照のネスト深さ、長い参照ファイルの目次欠落、Windows パス）。客観的かつ再現可能にするため、
同梱スクリプトを実行する:

```bash
python3 scripts/check_skill.py <スキルディレクトリのパス>
```

各機械チェックについて `PASS`/`FAIL`/`WARN` と該当値を1行ずつ出力し、レポートに折り込める JSON
ブロックも出す。機械チェックの結果はこの出力を信頼し、自分の注意力は下記の判断項目に回す。

### ステップ3: 定性項目を評価する

これらは実際の中身を読む必要があり、スクリプトでは判定できない。各項目について見解を持ち、
どの行が問題かを引用できるようにする。根拠は
[references/checklist.md](references/checklist.md) を参照。

- **description が発火するか** — 三人称で、_何をするか_ と _いつ使うか_ の両方を述べ、具体的な
  トリガー語を含むか。ここが最重要フィールド。曖昧ならスキルは発火せず、他がどれだけ良くても無意味。
- **簡潔か** — 本文はトークンに見合っているか、それとも Claude が既に知っていること（PDF とは
  何か、ライブラリの使い方）を説明していないか。水増しを指摘する。
- **自由度が適切か** — 壊れやすい/一貫性が要る手順には厳密なコマンドを、開かれたタスクには方針を。
  過剰な制約（柔軟なタスクへの無用な全大文字 MUST）と、精密さが要る箇所での曖昧な手振りの両方を
  指摘する。
- **具体例があるか** — 出力品質が重要な箇所では、抽象的な散文ではなく入出力ペアを。
- **用語が一貫しているか** — 1つの概念に1つの用語を通す。
- **時限情報がないか** — 「2025年8月以降は…」は腐る。歴史的な注記は「旧パターン」節へ。
- **選択肢ではなくデフォルトを1つ** — 逃げ道付きの推奨1本が「A・B・C・Dのどれでも」に勝る。
- **テンプレートと例が一致しているか** — 出力テンプレートと、直後に示す具体例が食い違っていないか
  （例: テンプレには見出しがあるのに例では省かれている等）。モデルに渡す目標像は1つに揃える。
- **スクリプトが解決しているか（丸投げでないか）** — 同梱スクリプトは自分でエラーを処理し、説明の
  ない「呪文定数」を避けているか。依存パッケージと MCP ツール名（`Server:tool`）は明示されているか。
- **評価（evals）があるか** — 公式は評価を先に作ることを推奨。無ければギャップとして記す。

### ステップ4: レポートを書く

次の構成をそのまま使う:

```
# スキルレビュー: <スキル名>

**総合判定:** <公開可 | 要改善 | 非準拠> — <一文で理由>

## チェックリスト
### フロントマター妥当性（ブロッカー）
- ✅/❌ <項目> — <値または理由>
...
### コア品質
- ✅/⚠️/❌ <項目> — <所見>
...
### スクリプト・コード（スクリプトが無ければ省略）
...
### テスト
...

## 優先修正（影響の大きい順）
1. **<問題>** — <なぜ重要か> → <具体的な変更。できれば書き換えた行そのもの>
2. ...
```

修正はチェックリストの順ではなく**影響の大きさ**で並べる。壊れた `name` 正規表現や曖昧な
`description` はブロッカー（スキルがロードされない/発火しない）、目次欠落は軽微な後押し。修正を
提案するときは実際の置き換えテキストを書く——書き換えた description やフロントマター行は
「description を明確に」より価値がある。すべて合格なら素直にそう言い、体裁のために問題を捏造しない。
