# スキルレビュー基準

以下の基準はすべて Anthropic 公式の Agent Skills ドキュメント（_overview_ と
_Skill authoring best practices_ ページ）に基づく。各項目は「何を確認するか」「機械的か
（スクリプトが担当）／判断が要るか（人＝モデルが担当）」、そして**なぜ重要か**を示す。良いレビュー
は理由を説明するものであって、ルールを引用するだけのものではない。

## 目次

- フロントマター妥当性（ブロッカー）
- description の質（最重要）
- 本文と構造
- 段階的開示（progressive disclosure）と参照
- コンテンツ指針
- スクリプト・実行コード
- テストと評価
- 重大度ガイド

## フロントマター妥当性（ブロッカー）

これらはドキュメント上のハード制約。違反するとスキルがロードされない/無効になるため、他がどれだけ
良くても「公開可」をブロックする。すべてスクリプトがチェックする。

- **`name` が存在**し、64文字以内。
- **`name` の文字種**: 小文字英字・数字・ハイフンのみ（`^[a-z0-9-]+$`）。日本語は不可。
- **`name` に予約語がない**: "anthropic" / "claude" を含んではいけない。
- **`name` に XML タグがない。**
- **`description` が存在**し、空でなく、1024文字以内、XML タグなし。

命名規約（判断項目・ブロッカーではない）: 動名詞形（`reviewing-skills`, `processing-pdfs`）が
望ましい。名詞句（`pdf-processing`）も可。曖昧な名前（`helper`, `utils`, `tools`, `data`）は
実際に問題——参照や把握がしにくくなる。

## description の質（最重要）

`description` は、100個以上あり得るスキルの中から Claude が発火可否を判断するときに**唯一**見る情報。
ここが間違っていると、スキルの中身は一切実行されない。重み付けを大きくする。

- **三人称。** description はシステムプロンプトに注入されるため、一人称/二人称（「〜をお手伝い
  します」「あなたは〜できます」「私が〜します」）は発見の問題を起こす。（スクリプトが WARN。）
- **「何を」と「いつ」の両方を述べる。** 「PDF からテキストを抽出する。PDF・フォーム・文書抽出に
  言及されたときに使う。」——能力だけでなくトリガー文脈も。
- **具体的なトリガー語。** 実ユーザーが打ちそうな語（ファイル種別・作業動詞・ドメイン名詞）を含める。
  曖昧な description（「文書を扱う」「データを処理する」）は発火しない。
- **アンダートリガー対策の押しの強さ。** Claude はスキルを*過少*使用しがち。トリガー句を列挙し
  「〜のときは必ず使う」と書いた description のほうが、簡潔すぎるものより確実に発火する。

## 本文と構造

- **500行以内**（スクリプトが超過で WARN）。超えたら参照ファイルへ分割。本文はスキル発火のたびに
  コンテキストに載るので、長さは毎回かかる税金。
- **簡潔——Claude は賢い前提。** 最も多い欠陥。各段落を疑う: これは Claude が既に知っている
  （PDF とは何か、pip の使い方）か？ プロジェクト固有・非自明な情報でない説明は削る。水増しは
  使用のたびにトークンを食う。
- **自由度が適切か。** 具体度を壊れやすさに合わせる:
  - _壊れやすい/一貫性が要る_（マイグレーション、厳密なコマンド列）→ 低自由度: 厳密なスクリプト、
    「このまま実行、フラグを足すな」。
  - _開かれた_（コードレビュー、分析）→ 高自由度: 方針を示しモデルを信頼。
  - *両方*の失敗を指摘する: 柔軟なタスクを縛る硬直した全大文字 MUST と、本当は精密さが要る箇所での
    曖昧な手振り。過剰な制約は過少な指定と同じく実在の欠陥。
- **ワークフローに明確なステップ。** 多段プロセスはコピー可能なチェックリストと番号付きステップが
  有効。特に検証/フィードバックループ（「検証→修正→繰り返し」）付きで。
- **「なぜ」を説明する。** 理由付きの指示（「テストアカウントは勝率を歪めるので除外」）は素の
  コマンドに勝る。理由なしの重い MUST/NEVER は黄信号。

## 段階的開示（progressive disclosure）と参照

- **参照は SKILL.md から1階層**（スクリプトがネストで WARN）。連鎖（a→b→c）で辿るファイルを
  Claude は部分的にしか読まないことがある（`head -100`）ため情報が欠ける。参照ファイルは
  すべて SKILL.md から直接リンクする。
- **100行超の参照ファイルには目次**（スクリプトが WARN）。部分読み時でも全体像が見えるように。
- **説明的なファイル名。** `doc2.md` ではなく `form_validation_rules.md`。索引ではなくドメインで
  整理（`reference/finance.md`）。
- **スクリプトの「実行 vs 参照」意図を明確に。** 「`analyze.py` を実行」（execute）か「アルゴリズム
  は `analyze.py` 参照」（read）か。曖昧だとトークンを浪費し誤動作を招く。

## コンテンツ指針

- **時限情報を入れない。** 「2025年8月以前は旧 API」は腐る。非推奨情報は折りたたんだ
  「旧パターン」節へ。
- **用語を一貫させる。** 1概念1用語（常に「field」、「box/element/control」を混ぜない）。
  不一致はモデルを混乱させる。
- **選択肢ではなくデフォルト1つ。** 「pdfplumber を使う」が「pypdf・pdfplumber・PyMuPDF・
  pdf2image のどれでも」に勝る。例外向けの狭い逃げ道付きで1つ推奨。
- **テンプレートと例の一致。** 出力テンプレートと直後の具体例が食い違わないこと（テンプレには
  見出しがあるのに例では省略、など）。モデルに渡す目標像を1つに揃える。
- **抽象より具体例。** スタイル/形式で出力品質が決まる箇所は、few-shot 同様に入出力ペアを示す。
- **スラッシュのみ**（スクリプトがバックスラッシュで WARN）。Windows パスは Unix で壊れる。

## スクリプト・実行コード

スキルにスクリプトが無ければこの節は丸ごと省略。

- **解決する、丸投げしない。** スクリプトは自分でエラー条件（ファイル無し、権限エラー）を処理すべき。
  投げっぱなしにして Claude に推測させない。例外を投げうる素の `open(path).read()` は丸投げ。
- **呪文定数を避ける。** マジックナンバー（`TIMEOUT = 47`）はコメントで正当化する。作者が値を
  説明できないなら Claude にも説明できない。
- **依存の明示。** パッケージが入っている前提にしない。必要パッケージを列挙し、実行環境の制約
  （API サンドボックスはネットワーク無し/実行時インストール無し）も記す。
- **完全修飾の MCP ツール名。** `ServerName:tool_name`（例 `GitHub:create_issue`）。接頭辞なしは
  複数 MCP サーバー存在時に「tool not found」を起こす。
- **ドキュメント付きスクリプト。** 各スクリプトが「何をするか・入力・出力形式」を述べる。
- **バッチ/高リスク操作には検証・検証可能な中間出力**（plan → validate → execute）。

## テストと評価

- **評価（evals）がある。** 公式は「本格的な文書化より先に評価を作る」「最低3シナリオ」を推奨。
  無ければ——ロードは妨げないが——ギャップとして記す。
- **使う予定の全モデルでテスト**（Haiku / Sonnet / Opus）。Opus に合う簡潔さが Haiku には
  足りないことがある。

## 重大度ガイド

レポートの「優先修正」の並べ替えに使う:

- **ブロッカー** — スキルがロードされない/発火しない: フロントマター妥当性の FAIL、または曖昧/
  不正な `description`。まずここを直す。解決するまで他は無意味。
- **重大（Major）** — 動くがコンテキストを浪費/誤動作する: 簡潔でない肥大した本文、誤った自由度、
  ネストした参照、丸投げスクリプト、出力品質が要るのに例が無い。
- **軽微（Minor）** — 仕上げ: 目次欠落、命名規約の細かな指摘、軽い用語ゆれ、evals 欠如。

完璧なスキルは存在してよい。合格ならそう言って止める——体裁のために軽微な指摘を作らない。
