# 設計書テンプレート

規模に応じて節を選ぶ。小さな変更は 1・3・6 だけで足りる。空の見出しは残さない。

## テンプレート

```markdown
# <タイトル>

- 状態: 提案 / 承認済み / 実装中 / 完了
- 日付: YYYY-MM-DD
- 規模: 小 / 中 / 大

## 1. 背景と課題

<何が困っているか。誰が、どんな場面で。>

## 2. 目標と非目標

- 目標: ...
- 非目標: ...（やらないこと）
- 成功条件: ...（測れる形で）

## 3. 検討した案

| 案         | 概要 | 利点 | 欠点・リスク | 工数 | 戻しやすさ |
| ---------- | ---- | ---- | ------------ | ---- | ---------- |
| A（推奨）  | ...  | ...  | ...          | ...  | ...        |
| B          | ...  | ...  | ...          | ...  | ...        |
| 何もしない | ...  | ...  | ...          | -    | -          |

**推奨: A。** 理由: ...

## 4. 設計（推奨案）

### コンポーネントと責務

### データモデル

### インターフェース（API / 関数 / CLI）

### 主要な流れ

### エラー時の挙動

## 5. セキュリティとプライバシー

<認証・認可、入力検証、秘密情報、個人情報、依存関係。design-review.md の観点を適用した結果。>

## 6. テスト戦略

<何を、どの層で、どうやって確かめるか。>

## 7. 移行とロールアウト

<既存データ・利用者への影響、段階的な展開、戻し方。>

## 8. リスクと未決事項

- リスク: ...（発生条件、影響、対処）
- 未決: ...（誰が、いつまでに決めるか）

## 9. 実装計画

1. ...（変更するファイル、テスト、検証コマンド）
```

## 書き方の例

悪い例（曖昧で検証できない）:

> エラー時は適切にリトライする。

良い例（数値と挙動が決まっている）:

> 外部 API が 5xx を返したら、1 秒、2 秒、4 秒の間隔で最大 3 回リトライする。それでも失敗したら、ジョブを `failed` にして、エラーを `job_errors` テーブルに記録する。4xx はリトライしない。
